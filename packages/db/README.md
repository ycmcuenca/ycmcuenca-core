# @ycmcuenca/db

The CMS's database adapter (design D1, D2, D3, D4 in
[`openspec/changes/content-store/design.md`](../../openspec/changes/content-store/design.md)).
It holds the schema, the migrations and the repository functions for `entries`
and their append-only `revisions`, on Drizzle ORM over `pg`. The running app
reaches it through Hyperdrive, as the least-privilege role `cms_runtime`.

## Why Drizzle's core query builder only

Code uses `pgTable`, `db.select()`, `db.insert()`, `db.update()` and
`db.transaction()`. It never calls `db.query.*` and never defines
`relations()`. Those belong to Drizzle's Relational Queries v1 API, which
Drizzle 1.0 removes (design D1, owner decision Q5). Keeping to the core builder
means the 1.0 upgrade is a version bump inside this package, not a rewrite of
every query. `eslint.config.js` enforces both restrictions.

## Migrations

Migrations are generated by `drizzle-kit` and applied by
`scripts/migrate.ts`, the one entry point used locally, in CI and by the
`admin` deploy. `scripts/migrate.ts` first ensures the `cms_runtime` role
exists, then applies the pending migrations, then verifies the runtime
privileges.

Three rules:

- **Forward-only.** Never edit or delete a migration that has been merged. The
  way to correct a mistake is a new migration.
- **Expand, then contract.** Add columns as nullable or with a default. Remove
  a column or a table only in a later release, after no released version of
  `admin` reads it. Every release must keep working for the previously
  released `admin`, so a rollback deploy stays safe
  ([expand and contract migrations](../../docs/SYSTEM_DESIGN.md#expand-and-contract-migrations)).
- **One concern per migration.** A migration that does two unrelated things is
  hard to reason about and hard to roll back.

### Adding a migration

1. Change `src/schema.ts`.
2. Generate the SQL and a snapshot beside it:

   ```sh
   bun run --filter @ycmcuenca/db db:generate -- --name <short-name>
   ```

3. Read the generated file and confirm it does only what you meant. Check the
   constraint and index names.
4. Apply and verify it locally:

   ```sh
   bun run db:prepare
   bun run test:integration
   ```

A change that is not a schema change — grants, for example — uses a custom
migration:

```sh
bunx drizzle-kit generate --custom --name <short-name>
```

then fill in the SQL by hand. `migrations/0001_runtime-grants.sql` is the
example: Drizzle does not model privileges, so the runtime role's grants live
there.

## Roles

- The **migrator** owns the schema and runs migrations. Locally that is the
  container's `postgres` superuser; in production it is the Neon project's
  owner role. Its connection string lives in `.env` (local), in the owner's
  shell and in the `NEON_MIGRATOR_URL` deploy secret.
- The **runtime** role, `cms_runtime`, is created by
  `scripts/ensure-runtime-role.ts` and granted its rights by
  `migrations/0001_runtime-grants.sql`: `USAGE` on `public`, `SELECT`, `INSERT`
  and `UPDATE` on `entries`, and `SELECT` and `INSERT` on `revisions`. It can
  never update or delete a revision, which is what makes the history
  append-only (design D3).

`scripts/check-privileges.ts` reads the catalog and compares every right
`cms_runtime` or `PUBLIC` holds — on tables, columns, sequences and schemas in
non-system schemas, plus its database rights, role attributes and memberships —
with an allow-list. It names each missing or unexpected right and exits
non-zero, so a grant made by hand is caught even when it is column-level. The
deploy runs it before uploading `admin`.

## Scripts

| Script               | What it does                                                |
| -------------------- | ----------------------------------------------------------- |
| `db:generate`        | Generates a migration from `src/schema.ts`.                 |
| `test`               | Unit tests. Needs no database.                              |
| `test:integration`   | Integration tests against `DATABASE_URL_TEST`.              |
| `bun run db:prepare` | Root script: creates the test database, then migrates both. |
| `bun run db:up`      | Root script: starts the local Postgres container.           |
